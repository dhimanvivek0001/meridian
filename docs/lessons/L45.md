# Lesson 45: Combine candidates + LightGBM ranker (closes M8)

Script: `scripts/reco_ranker.py` (about 4 minutes to run)
Module: M8 Recommender (lesson 4 of 4)

## The idea in one paragraph

Lessons 42-44 built three **candidate sources**: bestsellers, the customer's own recent items
(buy-again) and their basket partners. They then filled the 12 slots in a fixed order written
by hand. Real recommenders work in **two stages**:

1. **Retrieve**: collect a few dozen plausible items per customer from several sources.
2. **Rank**: a machine-learning model scores every candidate, and the top 12 are shown.

This lesson builds both stages and asks whether a learned order beats the hand-written one.

## The result first

| Recommender (12 items each)               | Hit rate   | vs L44 |
|-------------------------------------------|-----------:|-------:|
| L42 Popular only                          | 6.43%      |        |
| L43 Buy-again + popular                   | 10.65%     |        |
| L44 + bought-together pairs               | 11.37%     | baseline |
| L45 Hand rule on the wider candidate pool | 11.43%     | +0.06 pts |
| **L45 LightGBM ranker (2 training weeks)**| **11.52%** | **+0.15 pts (+1.4%)** |

The ranker wins, but only just. Read "The honest verdict" below before celebrating.

## Key words

- **Candidate**: one (customer, item) pair that *might* be recommended. One row per candidate.
- **Label**: 1 if the customer really bought that item in the target week, else 0.
- **Candidate recall**: share of buyers who bought at least one item from their candidate list.
  It is the **ceiling**: no ranking can score higher, because the ranker can only reorder
  what retrieval gave it.
- **Ranker / learning-to-rank**: a model trained to put the 1s above the 0s *within each
  customer's list*, rather than predicting each row in isolation.
- **Group**: the set of rows the ranker compares against each other (here, one customer's
  candidates for one week).

## Line by line

### Setup

```python
from datetime import date, timedelta
import numpy as np
import polars as pl
from lightgbm import LGBMRanker
```
`date`/`timedelta` let us say "the cut date minus 28 days". `LGBMRanker` is LightGBM's
learning-to-rank model. It's the same tree engine as the churn model in Lesson 29, with a
different goal.

```python
SEED = 45
np.random.seed(SEED)
```
Fixed seed. LightGBM samples rows and columns (`subsample`, `colsample_bytree`), so the
seed also goes into the model below. That way every run gives the same 11.52%.

```python
tx = pl.scan_parquet("data/clean/transactions.parquet")
ages = pl.read_parquet("data/clean/customers.parquet").select(["customer_id", "age"])
N_POP, N_PARTNERS = 50, 5
```
Lazy scan of all transactions, plus each customer's age. The candidate pool is **wider** than
in L44: 50 bestsellers instead of 12, and 5 partners per item instead of 3. With only
12 candidates there is nothing to rank. The ranker needs more options than slots.

```python
FEATURES = ["is_own", "is_partner", "is_pop", "own_n", "own_days", "pair_n", "pair_links",
            "pop_1w", "pop_prev_1w", "pop_4w", "pop_rank", "trend",
            "cust_lines", "cust_days", "age", "age_gap"]
```
The 16 clues the model sees for every candidate:

| Feature | Meaning |
|---|---|
| is_own / is_partner / is_pop | Which source(s) produced this candidate (1/0) |
| own_n | Times the customer bought this item in the last 4 weeks |
| own_days | Days since they last bought it |
| pair_n | Strongest basket-partner count linking it to one of their items |
| pair_links | How many of their own items it partners with |
| pop_1w, pop_prev_1w, pop_4w | Units sold last week, the week before, last 4 weeks |
| pop_rank | Bestseller position last week (1 = top) |
| trend | (last week + 1) / (week before + 1): rising or falling item |
| cust_lines | Customer's purchase lines in the last 4 weeks |
| cust_days | Days since the customer's last visit |
| age, age_gap | Customer age, and distance from the average age of the item's buyers |

### The `build(cut)` function: one week's candidates, features and labels

```python
def build(cut):
    d = lambda days: pl.lit(cut - timedelta(days=days))
```
Everything is relative to a cut date. `d(28)` means "28 days before the cut". Writing it
once as a function means the training weeks and the test week are built **identically**,
which prevents a whole family of bugs.

```python
    hist = tx.filter(pl.col("sale_date").is_between(d(28), d(1))).collect()
```
History = the 4 weeks before the cut. Only this is used for features.

```python
    label = (
        tx.filter(pl.col("sale_date").is_between(pl.lit(cut), pl.lit(cut + timedelta(days=6))))
        .select(["customer_id", "article_id"]).unique().with_columns(pl.lit(1).alias("label"))
        .collect()
    )
    buyers = label.select("customer_id").unique()
```
The 7 days from the cut on are the "answer" week. Each (customer, item) bought there gets
`label = 1`. `buyers` = everyone who bought that week. As in L42, we only score buyers.

```python
    pop = (
        hist.join(ages, on="customer_id", how="left")
        .group_by("article_id").agg(
            pl.col("sale_date").filter(pl.col("sale_date") >= d(7)).len().alias("pop_1w"),
            pl.col("sale_date").filter(pl.col("sale_date").is_between(d(14), d(8))).len().alias("pop_prev_1w"),
            pl.len().alias("pop_4w"),
            pl.col("age").mean().alias("item_age"),
        )
        .with_columns(
            pl.col("pop_1w").rank("ordinal", descending=True).alias("pop_rank"),
            ((pl.col("pop_1w") + 1) / (pl.col("pop_prev_1w") + 1)).alias("trend"),
        )
    )
```
One row per item with its popularity features. `.filter(...)` inside `agg` counts only
the rows of a given week. `item_age` = the average age of the people buying it. The `+ 1` in
`trend` avoids dividing by zero for brand-new items.

```python
    top = pop.sort(["pop_1w", "article_id"], descending=[True, False]).head(N_POP).select("article_id")
```
Top-50 bestsellers. The article ID breaks ties so the list is always the same.

```python
    own = hist.group_by(["customer_id", "article_id"]).agg(
        pl.len().alias("own_n"), (pl.lit(cut) - pl.col("sale_date").max()).dt.total_days().alias("own_days")
    )
```
Source 1 (buy-again from L43): every item each customer bought, with how often and how
many days ago.

```python
    basket = hist.select(["customer_id", "sale_date", "article_id"]).unique()
    partners = (
        basket.join(basket, on=["customer_id", "sale_date"], suffix="_p")
        .filter(pl.col("article_id") != pl.col("article_id_p"))
        .group_by(["article_id", "article_id_p"]).agg(pl.len().alias("n"))
        .filter(pl.col("n") >= 2)
        .sort(["article_id", "n", "article_id_p"], descending=[False, True, False])
        .group_by("article_id", maintain_order=True).head(N_PARTNERS)
    )
```
Source 2: exactly the L44 self-join (see L44.md for the walkthrough), now keeping the top 5.

```python
    pair = (
        own.select(["customer_id", "article_id"]).join(partners, on="article_id")
        .group_by(["customer_id", "article_id_p"]).agg(pl.col("n").max().alias("pair_n"), pl.len().alias("pair_links"))
        .rename({"article_id_p": "article_id"})
    )
```
Attach partners to each customer's own items. If two of a customer's items both point to the
same partner, we keep the strongest count (`max`) and note `pair_links = 2`. That's a stronger
signal.

```python
    popc = buyers.join(top, how="cross")
```
Source 3: a **cross join** gives every buyer all 50 bestsellers (72,019 x 50 = 3.6M rows
for the 9-15 Sep week).

```python
    own_b, pair_b = own.join(buyers, on="customer_id"), pair.join(buyers, on="customer_id")
```
Keep only customers who are buyers in the target week. Nobody else is scored.

```python
    cand = (
        pl.concat([own_b.select([...]), pair_b.select([...]), popc])
        .unique()
```
Stack the three sources and remove duplicates. If an item is both one of the customer's own
and a bestseller, it becomes **one** row.

```python
        .join(own_b, ...how="left").join(pair_b, ...how="left")
        .join(popc.with_columns(pl.lit(1).alias("is_pop")), ...how="left")
        .join(pop, on="article_id", how="left")
        .join(hist.group_by("customer_id").agg(... cust_lines, cust_days ...), how="left")
        .join(ages, on="customer_id", how="left")
        .join(label, on=["customer_id", "article_id"], how="left")
```
Bolt every feature onto each candidate. `how="left"` keeps every candidate even when there's no
match. For example, a bestseller the customer never bought gets `own_n = null`. LightGBM
handles nulls natively, and "null" itself carries meaning ("never bought this").

```python
        .with_columns(
            pl.col("own_n").is_not_null().cast(pl.Int8).alias("is_own"),
            pl.col("pair_n").is_not_null().cast(pl.Int8).alias("is_partner"),
            pl.col("is_pop").fill_null(0),
            pl.col("label").fill_null(0),
            (pl.col("age") - pl.col("item_age")).abs().alias("age_gap"),
        )
        .sort(["customer_id", "article_id"])
    )
    return cand, buyers.height
```
Turn "was there a match?" into 1/0 flags. A missing label means "not bought", so it becomes 0.
`age_gap`: a 25-year-old looking at an item bought mostly by 50-year-olds gets a gap of 25.
**Sorting by customer** matters: the ranker needs each customer's rows next to each other.

Before/after for one buyer (illustrative shape, using the real counts from the output):

| customer | article | is_own | is_partner | is_pop | own_days | pop_rank | label |
|---|---|---:|---:|---:|---:|---:|---:|
| A | own item | 1 | 0 | 0 | 3 | null | 0 |
| A | partner of it | 0 | 1 | 0 | null | null | 1 |
| A | bestseller #1 | 0 | 0 | 1 | null | 1 | 0 |
| ... about 60 rows per buyer | | | | | | | |

### Training data: two weeks, kept apart

```python
train_a, n_a = build(date(2020, 9, 2))
train_b, n_b = build(date(2020, 9, 9))
test, n_test = build(date(2020, 9, 16))
assert n_test == 68984, "same test buyers as Lessons 42-44"
```
Three "time machines": train on what happened in 2-8 Sep and 9-15 Sep, then test on 16-22 Sep.
The test week is never seen in training. The assert guarantees the same 68,984 test buyers
as before.

```python
train = pl.concat([
    train_a.with_columns(pl.col("customer_id") + "_w1"),
    train_b.with_columns(pl.col("customer_id") + "_w2"),
]).sort(["customer_id", "article_id"])
```
**Bug we hit and fixed.** Someone who bought in both weeks appears in both tables. Without
the `_w1`/`_w2` tag, their two weeks would be treated as one 120-row list. Worse, their rows
wouldn't sit next to each other, so the group sizes handed to LightGBM would describe the
wrong rows. A quick side experiment made exactly this mistake and showed an inflated 11.76%.
Tagging plus sorting makes each (customer, week) its own clean group.

| | Before tag | After tag |
|---|---|---|
| Customer X, 2-8 Sep | id = X | id = X_w1 |
| Customer X, 9-15 Sep | id = X | id = X_w2 |

```python
def recall(c):
    return c.group_by("customer_id").agg(pl.col("label").max())["label"].mean()
```
Per customer: did *any* candidate have label 1? Averaged over customers, this is the
ceiling. Real output: **test 23.96%**. So 76% of test buyers bought nothing we could
possibly recommend.

### Training the ranker

```python
fit = train.filter(pl.col("label").max().over("customer_id") == 1)
```
`.over("customer_id")` computes "max label within this customer" on every row. We keep only
customers with at least one 1. A list that is all 0s teaches a ranker nothing, because
there's nothing to put on top. That leaves 33,603 groups and 2,237,745 rows.

```python
groups = fit.group_by("customer_id", maintain_order=True).len()["len"].to_numpy()
assert groups.sum() == fit.height
```
`groups` is a list of group sizes, e.g. `[58, 61, 55, ...]`. It tells LightGBM that rows
0-57 are one customer, 58-118 the next, and so on. The assert checks the sizes add up to
every row.

```python
model = LGBMRanker(
    objective="lambdarank", n_estimators=300, learning_rate=0.05, num_leaves=31,
    min_child_samples=50, subsample=0.8, subsample_freq=1, colsample_bytree=0.8,
    random_state=SEED, deterministic=True, force_row_wise=True, verbose=-1,
)
model.fit(fit.select(FEATURES).to_numpy(), fit["label"].to_numpy(), group=groups)
```
- `objective="lambdarank"`: the model is rewarded for pushing bought items to the **top of
  each customer's list**, not for getting each row's probability right.
- `n_estimators=300, learning_rate=0.05, num_leaves=31`: 300 small trees, each nudging
  the scores a little (the same settings style as the churn model).
- `min_child_samples=50`: a leaf needs 50+ rows. This stops it from memorising rare cases.
- `subsample=0.8, colsample_bytree=0.8`: each tree sees a random 80% of rows and features.
  That reduces overfitting.
- `random_state`, `deterministic`, `force_row_wise`: make the result exactly repeatable.

### Scoring and comparing

```python
def top12_hit(c, score_col):
    top = c.sort(["customer_id", score_col], descending=[False, True]).group_by("customer_id", maintain_order=True).head(12)
    return top.group_by("customer_id").agg(pl.col("label").max())["label"].sum() / n_test
```
For each customer, take the 12 highest-scoring candidates and check for any hit. Divide by all
68,984 buyers.

```python
test = test.with_columns(pl.Series("score", model.predict(test.select(FEATURES).to_numpy())))
```
Score all 4.1M test candidates. The score has no unit; only the order within a customer matters.

```python
test = test.with_columns(
    (pl.col("is_own") * 1e9 + pl.col("own_n").fill_null(0) * 1e6
     + pl.col("is_partner") * 1e5 + pl.col("pair_n").fill_null(0) * 10 - pl.col("pop_rank").fill_null(9999) / 1e4).alias("rule")
)
```
**A fair opponent.** The ranker sees a *wider* pool than L44, so part of any gain could
come from the pool rather than the model. This builds the L44 hand rule as a single number on
the *same* pool. Huge multipliers make each tier dominate the next: own items first (most-bought
first), then partners (strongest first), then bestsellers (best rank first). Result: 11.43%.
So the wider pool alone added +0.06 points.


## What went wrong along the way (worth knowing)

1. **One training week lost.** The first version trained only on 9-15 Sep and scored
   10.93%, below L44. 16k customers was too little for the model to learn a reliable bestseller
   order, so it hurt the no-history group (5.52% vs 6.46%). Doubling the data fixed it.
2. **The group bug.** Stacking two weeks without tagging customers silently gave LightGBM
   wrong group boundaries, and a misleading 11.76%. If a number jumps, check the plumbing
   before you celebrate.
3. **A plain classifier did slightly better.** In a side test, `LGBMClassifier` (predict
   "bought? yes/no" per row, 10% of the 0s sampled) on the same two weeks scored 11.65%.
   Ranking objectives are not automatically better. With this little data the simpler
   objective was at least as good.

## The honest verdict

- The ranker beats the hand rule by **0.09 points: about 60 more buyers out of 68,984 got a hit**.
  That's small enough that a different week could reverse it. We haven't proved it's real.
- The **ceiling is 23.96%** candidate recall. The best possible ranking can't go above it, and
  we're at 11.52%. The bigger lever is **better candidates** (older history, similar-looking
  items from M9 images, similar descriptions from M10 text), not a cleverer order.
- The real value of the ranker is structural. New sources become new features, and the model
  works out how much to trust each one, so nobody has to hand-tune slot orders.

## What an interviewer might ask

**Q: Why two stages instead of scoring every item for every customer?**
A: 1.37M customers x 100k+ items is over 100 billion pairs, too many to score. Retrieval cuts
that to about 60 per customer (4M rows), cheap enough for a heavier model.

**Q: What is candidate recall and why report it?**
A: The share of buyers whose purchase is anywhere in their candidate list. It caps what the
ranker can achieve (23.96% here), and it tells you whether to work on retrieval or ranking.

**Q: Why did you remove customers with no positive label from training?**
A: Lambdarank learns from comparisons *within* a group: "this bought item should be above that
one". If nothing was bought, there is no comparison to learn from, so those rows only cost
time.

**Q: How did you avoid leakage?**
A: Every feature for a week comes only from the 28 days before its cut date, built by one shared
`build()` function. Labels come only from the 7 days after. The test week (16-22 Sep) is never
used in training.

**Q: Your ranker beat the baseline by 0.09 points. Is that significant?**
A: Probably not proven. It's about 60 customers out of 69k. I'd check with a paired test (count
customers where the ranker hit and the rule missed, and vice versa: McNemar's test), or repeat
on several test weeks. I'd report it as "at least as good, more extensible" rather than a win.

**Q: Ranker vs classifier, which would you choose?**
A: Here the classifier did slightly better (11.65% vs 11.52%), and it's simpler to explain and
debug. Rankers usually pull ahead with more training data and when the position within the top
12 matters (metrics like MAP@12). I'd keep both in the experiment and decide on several weeks.

**Q: Why does the ranker hurt customers with no history?**
A: For them every candidate is a bestseller, so the model can only reorder the top 50 using
weak clues (age gap, trend). With limited training data that reordering is noisier than
plain popularity. A fix is a separate fallback, so customers without history just get
bestsellers. Another is better cold-start features such as age-band bestsellers.
