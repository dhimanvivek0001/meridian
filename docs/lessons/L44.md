# Lesson 44: "Bought together" recommender

Script: `scripts/reco_bought_together.py`
Module: M8 Recommender (lesson 3 of 4)

## The idea in one paragraph

In Lesson 43, each customer was shown the items they had bought in the last 4 weeks
("buy again"), and the week's 12 bestsellers filled any empty slots. The hit rate was 10.65%.
Most customers have only about 4-5 recent items, though, so around 7 of the 12 slots
went to generic bestsellers. This lesson fills those slots with something more personal:
items that other shoppers **put in the same basket** as the customer's own items.
This is the "customers who bought this also bought..." idea you see on shopping sites.

## The result first

| Recommender (12 items each)          | Hit rate | vs previous |
|--------------------------------------|---------:|------------:|
| L42 Popular only                     | 6.43%    | baseline    |
| L43 Buy-again + popular              | 10.65%   | +66%        |
| L44 Pairs + popular (no buy-again)   | 8.62%    | (test only) |
| **L44 Buy-again + pairs + popular**  | **11.37%** | **+0.72 pts (+6.8%)** |

"Hit rate" = share of the 68,984 test-week buyers (16-22 Sep 2020) who bought at least
one of the 12 items we showed them.

## Key words

- **Basket**: everything one customer bought on one day. H&M data has no receipt number,
  so "same customer + same day" is our best guess at one shopping trip.
- **Pair**: two different items found in the same basket.
- **Partner**: for item A, the items most often paired with A.
- **Candidate source**: one way of producing items to recommend (bestsellers, buy-again,
  pairs). Real systems combine several.

### Step 3: build baskets and count pairs

```python
recent = (
    tx.filter(pl.col("sale_date").is_between(pl.date(2020, 8, 19), pl.date(2020, 9, 15)))
    .select(["customer_id", "sale_date", "article_id"])
    .unique()
    .collect()
)
```
- Same 4-week window as buy-again (19 Aug to 15 Sep). Only data from **before** the test
  week is used, so we are not peeking at the answers.
- `select`: keep only the 3 columns we need.
- `unique()`: if someone bought 2 of the same T-shirt in one trip, keep one row. Otherwise
  the T-shirt would "pair with itself" and get counted twice.

Output: 963,309 basket lines in 338,026 baskets (about 2.8 items per basket).

```python
pairs = (
    recent.join(recent, on=["customer_id", "sale_date"], suffix="_partner")
    .filter(pl.col("article_id") != pl.col("article_id_partner"))
    .group_by(["article_id", "article_id_partner"]).agg(pl.len().alias("n_baskets"))
)
```
This is the core trick, a **self-join**: the table is joined to itself on
"same customer, same day". Every item in a basket gets matched with every item in that
same basket.

Toy example (made-up basket of 3 items) to show the shape:

Before (one basket):

| customer | day    | article |
|----------|--------|---------|
| C1       | 10 Sep | Haley dress |
| C1       | 10 Sep | Mary dress  |
| C1       | 10 Sep | Cilla dress |

After the self-join, 3 x 3 = 9 rows. The `filter` then drops the 3 rows where an item
meets itself, leaving 6:

| article     | article_partner |
|-------------|-----------------|
| Haley dress | Mary dress      |
| Haley dress | Cilla dress     |
| Mary dress  | Haley dress     |
| Mary dress  | Cilla dress     |
| Cilla dress | Haley dress     |
| Cilla dress | Mary dress      |

Both directions are kept on purpose: we want to be able to look up partners of *either*
item. `group_by(...).agg(pl.len())` then counts in how many baskets each pair appeared.
Real output: **2,970,330 distinct pairs**.

```python
partners = (
    pairs.filter(pl.col("n_baskets") >= 2)
    .sort(["article_id", "n_baskets", "article_id_partner"], descending=[False, True, False])
    .group_by("article_id", maintain_order=True).head(3)
)
```
- `n_baskets >= 2`: a pair seen only once is probably coincidence (one person happened to
  buy socks and a coat), so we drop it.
- `sort`: within each item, put the most frequent partners first. The partner ID is a
  final tie-breaker so the order is always the same.
- `group_by(..., maintain_order=True).head(3)`: keep the top 3 partners per item.

Result: **13,363 items** have at least one partner.

### Step 4: fill the 12 slots

```python
def recommend(c, use_again=True, use_pairs=True):
    own = list(again.get(c, []))
    picks = list(own) if use_again else []
```
`again.get(c, [])` returns the customer's own items, or an empty list if they had no recent
purchase. The `use_...` switches let us turn sources off to measure each one's value.

```python
    if use_pairs:
        for a in own:
            for p in partner_of.get(a, []):
                if len(picks) < 12 and p not in picks:
                    picks.append(p)
```
For each own item (most important first), add its partners. Skip any partner already in
the list, and stop at 12.

```python
    for a in top12:
        if len(picks) >= 12:
            break
        if a not in picks:
            picks.append(a)
    return picks[:12]
```
Whatever slots remain go to bestsellers. `[:12]` is a safety cap.

Example customer journey (from the averages in the output):

| Slot source  | Before (L43) | After (L44) |
|--------------|-------------:|------------:|
| Own items    | ~4.6         | ~4.6        |
| Partners     | 0            | up to ~7    |
| Bestsellers  | ~7.4         | the rest    |

```python
def hit_rate(**kw):
    hits = 0
    for c, bought in zip(test["customer_id"], test["bought"].to_list()):
        if set(bought) & set(recommend(c, **kw)):
            hits += 1
    return hits / test.height
```
For every test buyer, build their 12 picks. `set(a) & set(b)` is the overlap between what
they bought and what we showed. If it is non-empty, that's a hit. `**kw` passes the
on/off switches straight through to `recommend`.

## Why the gain is "only" +0.72 points

1. 55% of test buyers have no recent purchase, so pairs can't help them.
2. Partners *replace* bestsellers. Some of those bestsellers were hits, so we win some
   and lose some.
3. The slot order is fixed by hand (own, then partners, then bestsellers). A partner seen in 62
   baskets may deserve to beat a bestseller, while one seen in 2 may not. Learning
   that trade-off from data is exactly what the LightGBM ranker in Lesson 45 does.

## What an interviewer might ask

**Q: How did you define a basket without an order ID?**
A: Same customer on the same day. It's an approximation: an online and an in-store order on
the same day get merged. But it's the standard choice for this dataset and it's easy to explain.

**Q: Why did you drop pairs seen only once?**
A: With about 3 million pairs, most single co-occurrences are noise. A minimum count is
a simple way to keep only repeated behaviour. The threshold (2) could be tuned on a
validation week.

**Q: Isn't raw co-occurrence count biased toward bestsellers?**
A: Yes. A hugely popular item shows up in many baskets just by being popular. Fixes include
lift (how much more often A and B appear together than chance would predict), cosine
similarity, or normalising by the partner's popularity. We kept raw counts as the simple
first version. Trying lift would be a good next experiment.

**Q: How do you know you're not leaking the future?**
A: Every input (pairs, buy-again, bestsellers) uses only data up to 15 Sep 2020. The test
week starts 16 Sep. The 68,984 test buyers are fixed by an assert.

**Q: Why is hit rate a reasonable metric, and what's its weakness?**
A: It's easy to explain ("did they buy anything we showed?"). But it ignores *where* in the list
the hit was and how many hits there were. Ranking metrics like MAP@12 (the H&M competition
metric) or recall@12 reward putting the right items first.

**Q: Self-joins can explode. How big did it get?**
A: The rows grow with basket size squared. With 338k baskets averaging about 2.8 items it stayed
small (about 3M pairs, 4 seconds). On a full year you would limit the window, cap the
basket size, or sample.
