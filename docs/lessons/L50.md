# Lesson 50: GenAI - writing product tags with a free local language model

Script: `scripts/genai_tags.py` (about 17 minutes on CPU, plus a one-time 727 MB model download)
Module: M10 NLP / GenAI (lesson 3 of 3, closes M10)

## The idea in one paragraph

L49 showed that new items can be recommended from their **descriptions**. But many shops have
thin or messy product text. Can a **generative AI** model write short shopping **tags** and a
one-line **summary** for each new item? The rule was: no paid API, only a **free model that runs
on this laptop**. We test it honestly: does it follow the instructions, is it fast enough, and,
most importantly, **does it make things up?** We compare it against a no-AI baseline: the 5
most important words by TF-IDF (L48).

## The result first

100 new products (from L49's test-week launches), one colour each:

| | TF-IDF top-5 words (no AI) | SmolLM2 tags | SmolLM2 summary |
|---|---:|---:|---:|
| Words grounded in the source text | **100%** | 88.4% | 68.2% |
| Product type guessed from this text alone | 20.0% | 22.0% | 57.0%* |
| Followed the length instruction | always 5 | 12% gave exactly 5 | 38% kept to 15 words |
| Time per item (CPU) | instant | 9.8 s for tags + summary | (included) |

\* For reference, the **full description** scores 50.0%. The summary beats it only because we gave
the model the product type in the prompt and it often repeats it ("Dark blue boxer shorts...").
The same goes for colour: it is mentioned in 97% of outputs, but we told it the colour.

Real examples:

| Item | TF-IDF (no AI) | SmolLM2 tags | SmolLM2 summary |
|---|---|---|---|
| Boxer shorts in cotton jersey with short legs, an elasticated waist and lined front | boxer, shorts, legs, elasticated, short | jersey, cotton, short legs (dark blue), elasticated, front | Dark blue boxer shorts with short, elasticated legs and lined fronts for a comfortable and stylish summer bottom. |
| Moulded eye mask in velour-covered plastic with rabbit ears on top and an elastic strap | rabbit, mask, ears, velour, moulded | velour-plastic, eye mask, rabbit ears, elastic strap | Black **velvet**-covered eye mask with rabbit-ear straps and elastic back for a stylish night out. |
| Cargo joggers in stretch cotton twill with an elasticated drawstring waist, side pockets and flap back pockets | cargo, shaping, leg, knees, joggers | cargo jogger, stretch cotton, twill, elasticated, drawstring | Dark blue stretch cotton trousers with elasticated waist, **shoulder-pockets**, and a flap-back design for a comfortable and stylish **summer** look. |

The LLM reads more naturally ("cargo jogger", "stretch cotton" are real shopping phrases;
TF-IDF picks odd single words like "shaping", "knees"). But it **invents**: velour becomes
"velvet", joggers get "shoulder-pockets", and a September launch becomes "summer".

**Verdict:** a free 360M-parameter model writes useful **drafts**. About 1 in 9 tag words and 1 in 3
summary words are not backed by the description. Use it with a human check or an automatic
grounding filter, not unsupervised. For search tags only, TF-IDF keywords are about as useful and
never invent.

## Key words

- **LLM (large language model)**: a neural network trained to predict the next word. "Instruct"
  versions are further trained to follow instructions in a chat format.
- **SmolLM2-360M-Instruct**: a small, free, open model from Hugging Face with 362 million
  parameters (Apache-2.0 licence, so commercial use is allowed). ChatGPT-class models are hundreds of
  times bigger. We picked it because it is **727 MB** and runs on a CPU. Qwen2.5-0.5B was
  exactly 1.0 GB, on our download limit.
- **Prompt**: the text we give the model. **Few-shot prompting**: including a worked example
  (question + ideal answer) before the real question.
- **Greedy decoding**: always pick the single most likely next word. No randomness, so the same
  input always gives the same output (our "fixed seed" for text).
- **Hallucination**: fluent text that isn't supported by the input.
- **Grounding rate**: our hallucination check, the share of output words that appear in the
  description, colour or product type.

## What went wrong first (and the fix)

The first version asked for both things in one prompt:

```
Reply in exactly this format and nothing else:
Tags: five short lowercase tags, comma separated
Summary: one catchy sentence of at most 15 words
```

Result after 20 minutes of generation: **0% usable**. The probe showed why. The model either just
rewrote the description...

```
'Tights in a soft, fine-knit cotton blend with an elasticated waist.'
```

...or copied the instructions back:

```
'five short lowercase tags, comma separated\nTags: five short lowercase tags, comma separated\n...'
```

A 360M model is too small to juggle a multi-part format. Three changes fixed it:

| Change | Why |
|---|---|
| One task per prompt (tags, then summary separately) | Small models handle one simple instruction much better |
| One worked example (a made-up pair of denim shorts) | The model copies the *pattern* of the answer |
| Short `max_new_tokens` (25 / 35) | Less room to ramble |

A test run then showed greedy decoding **looping**: "...calf-length, calf-high, V-neck, V-neck,
V-neck, V". Adding `no_repeat_ngram_size=3` (never repeat the same 3-token phrase) is the
standard fix. We also **cache** the generated text to `data/clean/genai_raw.parquet`, so a crash
in the scoring code (which happened: a list + string bug) never costs another generation run.

**Lesson: test on 3 items before running on 100.** We lost 20 minutes by not doing that.

```python
tok = AutoTokenizer.from_pretrained(MODEL)
lm = AutoModelForCausalLM.from_pretrained(MODEL, dtype=torch.float32)
lm.eval()
```
Load the tokenizer and model from the local cache (downloaded once, 727 MB). `float32` is the
normal CPU number format. `eval()` switches off training-only behaviour.

```python
EX_IN = "Product: Shorts (Light Blue). Description: Shorts in washed denim with a high waist, zip fly and raw-edge hems."
TASKS = {
    "tags": ("Give 5 short lowercase shopping tags for the product, comma separated. Only use facts from the description.",
             "denim, shorts, high waist, light blue, raw edge", 25),
    "summary": ("Write one catchy sentence (at most 15 words) to sell the product. Only use facts from the description.",
                "Light blue high-waisted denim shorts with raw-edge hems for easy summer style.", 35),
}
```
The **few-shot example**: a made-up product (not from our data, so we don't leak a real answer)
and the ideal answer for each task. Each task has an instruction, an example answer and a maximum
output length in tokens. A token is roughly three-quarters of a word.

```python
def generate(task, r):
    inst, ex_out, max_new = TASKS[task]
    q = f"Product: {r['product_type_name']} ({r['colour_group_name']}). Description: {r['detail_desc']}"
    chat = [{"role": "system", "content": inst}, {"role": "user", "content": EX_IN},
            {"role": "assistant", "content": ex_out}, {"role": "user", "content": q}]
    ids = tok(tok.apply_chat_template(chat, tokenize=False, add_generation_prompt=True), return_tensors="pt")
    gen = lm.generate(**ids, max_new_tokens=max_new, do_sample=False, no_repeat_ngram_size=3, pad_token_id=tok.eos_token_id)
    return tok.decode(gen[0, ids["input_ids"].shape[1]:], skip_special_tokens=True).strip()
```
- `chat` is a pretend conversation. The **system** message gives the rule, then an example question
  and answer, then the real question.
- `apply_chat_template` converts that into the exact text format the model was trained on
  (special markers between turns). `add_generation_prompt=True` ends with "assistant's turn
  now".
- `tok(...)` turns the text into token numbers.
- `generate`: `do_sample=False` = greedy (repeatable); `no_repeat_ngram_size=3` stops loops;
  `pad_token_id` silences a warning.
- `gen[0, len(input):]` keeps only the **new** tokens (the model returns prompt + answer);
  `decode` turns them back into text.

```python
rows = list(items.iter_rows(named=True))
if os.path.exists(CACHE) and pl.read_parquet(CACHE)["article_id"].to_list() == items["article_id"].to_list():

            raw_sum.append(generate("summary", r))
```

The cache. If saved generations exist **for exactly these 100 items**, reuse them; otherwise
generate (about 17 minutes) and save. `no_grad()` skips training bookkeeping. The ID-list check
means changing the sample can never silently reuse the wrong text.

- Split tags on commas, strip stray punctuation, lowercase, drop empties, and **keep the first 5**.
- `n_raw` counts how many tags the model actually gave (median **8**, though we asked for 5).
- `n_words` is the summary length (median **18**, though we asked for at most 15).

Small models are loose with counts, so always enforce limits in code.

```python
words = lambda s: {w.rstrip("s") for w in re.findall(r"[a-z]{3,}", s.lower())}

def grounded(tag_str, r):
    src = words(f"{r['detail_desc']} {r['colour_group_name']} {r['product_type_name']}")
    w = words(tag_str)
    return len(w & src) / len(w) if w else np.nan
```
The **hallucination check**.
- `words` makes a set of lowercase words of 3+ letters, with a trailing "s" removed (so "pocket" =
  "pockets").
- `grounded` = the share of output words that also appear in the source (description + colour +
  type).

A real example:

| Output | Words not in the source | Grounded |
|---|---|---:|
| Tags "pink, shimmery tulley, glitter, elastic, bow" for "Flared skirt in glittery tulle. Shimmering elastic waistband with a sewn-on bow." | shimmery, tulley, glitter | 50% |

It's strict: "glitter" vs "glittery" counts as a miss. So 88% is a **lower bound** on true
accuracy; but "tulley" (a typo) and "velvet" (a wrong fabric) are real errors.

```python
colour_hit = np.mean([r["colour_group_name"].lower().split()[-1] in f"{t} {s}".lower() for t, s, r in zip(llm_tags, summary, rows)])
```

like "Underwear bottom" are hard to match), so treat this as a relative comparison only.

## What an interviewer might ask

**Q: Why a local model instead of an API like GPT or Claude?**
A: The brief was zero cost, and local also means product data never leaves the machine, with no rate
limits and no per-call fees. The trade-off is quality: a 360M model invents details and ignores
length limits. In production I'd compare a few models on the same grounding metric. Bigger models
or an API would likely hallucinate less, at a cost per item I can estimate up front.

**Q: How did you measure hallucination?**
A: Grounding rate: the share of output words present in the source description, colour or type.
It's cheap, automatic and strict (misses synonyms), so it's a lower bound. Tags 88%, summaries
68%. I also printed the worst cases: "shoulder-pockets" on joggers, "velvet" for velour. Stronger
options: an NLI model that checks each claim against the source, or human review of a sample.

**Q: The model ignored "5 tags" and "15 words". What do you do?**
A: Don't trust the model to count; enforce it in code (keep the first 5 tags, truncate or
regenerate long summaries). Few-shot examples helped (0% to 100% usable format), and constrained
decoding (grammars, JSON mode) can force a format.

**Q: Why did the first prompt fail completely?**
A: A tiny model can't follow a multi-part output format; it echoed the instructions. One task per
prompt plus one worked example fixed it. I should have tested on 3 items first; I lost a
20-minute run.

**Q: Is it fast enough for the whole catalogue?**
A: 9.8 s per item on a laptop CPU, so 105k articles would take about 12 days. Options: batch several
items per call, use a GPU (roughly 50-100x faster), quantise the model, or only generate for new
items (a few hundred a week, which takes about an hour on CPU).

**Q: Would you ship it?**
A: As a drafting tool for merchandisers, yes, with a grounding filter that flags outputs below
some threshold for review. Not as unsupervised customer-facing copy: a wrong fabric ("velvet")
on a product page is a returns and trust problem.
