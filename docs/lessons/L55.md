# Lesson 55: A reproducible weekly scoring pipeline

Script: `scripts/weekly_pipeline.py [cutoff] [--drill]` (about 1.5 minutes per week)
Module: M12 MLOps (lesson 2 of 3)

## The idea in one paragraph

A churn model is only useful if it runs **every week, on fresh data, safely**. A production batch job
does the same steps in the same order every time:

1. **check the data** (and stop if it's broken);
2. build features with **the same code used in training**;
3. load the **approved ("champion") model** from a registry;
4. check whether this week's data looks like the training data (**drift**);
5. score customers and assign **audiences**;
6. record what happened.

And it must be **reproducible**: run it twice on the same week, get byte-identical output.

## Key words

- **Batch pipeline**: a script that processes a whole batch (here, a week) on a schedule.
- **Data check / data contract**: a rule the input must satisfy. **Hard** check: failing it stops
  the run. **Soft** check: failing it only warns.
- **Model registry**: a catalogue of approved model versions. An **alias** like `@champion` points
  at the version to use, so the pipeline never hard-codes "version 1"; promoting a new model is just
  moving the alias.
- **Drift**: this week's data looks different from the training data, so the model may be wrong.
- **PSI (Population Stability Index)**: a number for "how much did a distribution move". Rule of
  thumb: below 0.1 stable, 0.1-0.2 some shift, above 0.2 big shift.
- **Fingerprint**: a short code computed from the output. Same fingerprint = same output.
- **Fire drill**: deliberately breaking something to prove the alarm works.

## How PSI works (illustration)

Split the training data into 10 equal-sized bins (each holds 10% of customers). Then see what share
of *this week's* customers fall in each bin:

| Bin | Training share (r) | This week (c) | (c - r) x ln(c / r) |
|---|---:|---:|---:|
| 1 | 10% | 10% | 0.000 |
| 2 | 10% | 5% | 0.035 |
| 3 | 10% | 15% | 0.020 |
| ... | ... | ... | ... |

PSI = the sum of the last column. If the distribution hasn't moved, every term is 0. (Made-up numbers to show
the formula; the real results are below.)

## The fire drill: why you must watch inputs, not just outputs

We pretended an upstream system changed `online_share` from a fraction (0.91) to a percentage (91)
and shifted ages by 10 years:

| | Normal week | Drill (bug injected) |
|---|---:|---:|
| PSI online_share | 0.000 | **2.226** (WARN) |
| PSI age | 0.001 | **2.574** (WARN) |
| PSI predicted risk | 0.002 | **0.024** (looks fine!) |
| winback_voucher | 259,380 | 299,609 (+40,229) |
| no_action | 157,903 | 100,218 (-57,685) |

The **model's output barely moved** (PSI 0.024 is "stable"). Decision trees treat 91 the same as 1:
both are "above the highest split". But 40,000 extra customers would get a voucher. If we only
monitored the output we'd miss the bug; **feature-level** drift checks catch it.

On real weeks, drift was always low (highest PSI 0.042 for 1 Oct 2019, 0.011 for the 14 Apr 2020
lockdown week). Our features are mostly 12-month totals that move slowly, so in practice this alarm
is mainly a **bug detector**.

## Two things that went wrong first

**1. The volume check stopped real weeks.** At first every check was "stop if it fails". The volume
check (last week's rows within 50-150% of the usual) fired on the Easter 2020 sale and the 28 Sep 2019
spike. Those are real, not broken data, and skipping the weekly scoring because of a sale is wrong.
Fix: **hard** checks (stale data, nulls, invalid values, missing IDs) stop the run, and **soft**
checks (volume) warn.

**2. The same week gave different output.** Two runs gave fingerprints `0a055f92f638` and
`d776538cbf28`, with identical audience counts. The cause: the `spend` feature is a sum over many
rows, and polars adds rows on several threads in varying order. Floating-point addition isn't
exactly associative, so the sum differs in the **14th decimal**. That flipped a customer sitting
exactly on a rounding or rule boundary. Fix: round all float features to 9 decimals before scoring.
After that, 3 runs → `1187941fd28b`, byte-identical files. (How small is the noise? Re-building the
training file gave a largest `spend` difference of 0.000000000000011 across 988,844 customers.)

**The most important line.** The pipeline builds features with *exactly* the code used to build the
training data. A common production bug is "training-serving skew": someone rewrites the features
for production slightly differently (e.g. 30-day vs 4-week window) and the model quietly gets worse.
To make this import possible we refactored `churn_data_v2.py`: the logic moved into
`make_features()`, and the file-writing part only runs when the script is run directly
(`if __name__ == "__main__":`). Re-building the training files with the refactored code gave the same
values (only those 1e-14 float differences).

```python
def psi(ref, cur, bins=10):
    edges = np.unique(np.quantile(ref, np.linspace(0, 1, bins + 1)))
    edges[0], edges[-1] = -np.inf, np.inf
    r = np.histogram(ref, edges)[0] / len(ref)
    c = np.histogram(cur, edges)[0] / len(cur)
    r, c = np.clip(r, 1e-4, None), np.clip(c, 1e-4, None)
    return float(((c - r) * np.log(c / r)).sum())
```
- Bin edges are the training data's deciles. `np.unique` merges duplicate edges: for a feature like
  `club_active` (only 0 or 1) there are just 2 bins.
- The outer edges become -inf/+inf, so this week's values outside the training range still land in a bin.
- `clip(1e-4)` avoids log(0) for an empty bin.

Audiences by priority. A voucher goes to customers whose expected **margin** gain is positive (the L51
correction). Others at high risk get a free email. Safe big spenders get early access. Everyone else
gets nothing. The `when` chain gives each customer exactly one audience, and the assert proves it.

## What an interviewer might ask

**Q: What's training-serving skew and how did you prevent it?**
A: Features computed differently in production than in training. I import the exact
`make_features()` used to build the training set, and the registered model is tagged with its feature list,
which the pipeline checks before scoring.

**Q: Which data checks stop the pipeline and which only warn?**
A: Stop: stale data, nulls in keys, impossible values, unknown IDs (the data is broken, so scoring
would be wrong). Warn: unusual volume. I learned that the hard way: a volume stop fired on the Easter
sale and a real spike, and skipping a week's scoring for a sale is worse than scoring it.

**Q: How do you know your drift check works if real drift is low?**
A: A fire drill. I injected a plausible upstream bug (a share sent as a percentage, age shifted).
Feature PSI jumped to 2.2-2.6, but the model's output PSI stayed at 0.024, even though 40,000 extra
customers would have got a voucher. So monitor the inputs, not only the predictions.

**Q: Your pipeline gave two different outputs for the same week. Why?**
A: Multi-threaded floating-point sums differ in the 14th decimal between runs, which can flip a
borderline customer. I round features to 9 decimals and compare output fingerprints; three runs
were then byte-identical. Exact reproducibility makes audits and debugging possible.

**Q: How would you promote a new model?**
A: Train a challenger, log it to MLflow, compare it on the same holdout (and ideally in a shadow run
on live weeks), then move the `@champion` alias. The pipeline code doesn't change, and rollback is
moving the alias back.
