# Lesson 54: MLflow - keeping track of every model you train

Script: `scripts/mlops_tracking.py` (about 10 minutes; most of it is re-running the L45 ranker)
Module: M12 MLOps (lesson 1 of 3)

## The idea in one paragraph

So far our results lived in printouts and in `findings.md`. If someone asks "which settings gave
AUC 0.796, on which data, with which code?", we'd have to dig. **MLflow** is a free tool that
records every training **run**: its settings (*params*), results (*metrics*), the saved model
file (*artifact*), and *tags* such as the git commit. Then you compare runs side by side in a web
page. We log the churn models from L16-L19 and the L45 ranker, plus a few variants. On the way,
tracking caught a real bug: **the L45 ranker gave a different answer each time it ran**.

Better **clues** (5 → 13) helped more than any model setting. Tuning moves the 4th decimal.

**The bug tracking found.** Every logged run of the *unchanged* L45 ranker:

| Run | Code | Buyers hit | Hit rate |
|---|---|---:|---:|
| 1 | original | 7,968 | 11.55% |
| 2 | original | 7,938 | 11.51% |
| 3 | **fixed** | 7,962 | 11.54% |
| 4 | **fixed** | 7,962 | 11.54% |

Same code, same data, same seed, yet a different answer each time, until we fixed one line.

## Key words

- **Run**: one training job. **Experiment**: a folder of related runs (here `meridian-churn`,
  `meridian-reco-ranker`).
- **Params**: the settings you chose (trees, learning rate). **Metrics**: the results (AUC, hit
  rate). **Artifacts**: files (the model, a feature-importance table). **Tags**: labels (lesson,
  git commit, batch).
- **Tracking store**: where MLflow keeps all of this. Ours is a small SQLite database file,
  `data/mlflow/mlflow.db`, with model files beside it. It's inside `data/`, so it's never committed.
- **Reproducible**: same code + same data + same seed = same result, every time.
- **Data fingerprint (md5)**: a short code computed from a file's bytes. Change one byte and it
  changes, so the run records exactly which data it saw.

## How to look at it

```
.venv\Scripts\mlflow ui --backend-store-uri sqlite:///data/mlflow/mlflow.db
```
Then open http://127.0.0.1:5000. Click an experiment, tick several runs, and press **Compare**: you get
the params and metrics side by side, plus charts (e.g. AUC vs num_leaves). Each run also shows its
`feature_importance.json` and the saved model under *Artifacts*.

## The reproducibility bug

In `reco_ranker.py` (L45), the popularity rank of each item was computed with:

```python
pl.col("pop_1w").rank("ordinal", descending=True).alias("pop_rank")
```

"Ordinal" gives tied items (same sales last week) *different* ranks, in **the order the rows happen
to be in**. That order comes from a `group_by`, and polars runs `group_by` on several CPU threads,
so the row order changes from run to run. An illustration (made-up items):

| Item | Sold last week | pop_rank, run 1 | pop_rank, run 2 |
|---|---:|---:|---:|
| A | 412 | 7 | 8 |
| B | 412 | 8 | 7 |

`pop_rank` is a **model feature**, so the model's training data changed, and with it the trees and the
hit rate. The fix sorts first, so ties are always broken by article ID:

```python
.sort(["pop_1w", "article_id"], descending=[True, False])
.with_columns(pl.int_range(1, pl.len() + 1).alias("pop_rank"), ...)
```

After the fix, two runs gave exactly 7,962 each. Why it matters: the run-to-run wobble before the fix (30
buyers, 0.04 points) was **a third** of the ranker's whole advantage over the hand rule (0.12
points). Without tracking we'd never have seen it; we'd just have one number, 11.52%.

```python
def md5(path):
    h = hashlib.md5()
    with open(path, "rb") as f:
        for chunk in iter(lambda: f.read(1 << 20), b""):
            h.update(chunk)
    return h.hexdigest()[:12]
```
The data fingerprint. It reads the file 1 MB at a time (so a 500 MB file doesn't fill memory) and keeps the
first 12 characters, e.g. `7cfc219df589`.


- `BATCH`: one ID per script execution (e.g. `20261123-025204`), so the comparison table only shows this
  execution's runs, even though older ones stay in the store.

  everything imported and even listed torch.
- `GIT`: the code version. If any script has uncommitted changes, it adds `-dirty`, an honest
  warning that this run can't be traced to a commit exactly. Our post-fix runs say `bbd843c-dirty`
  because the fix wasn't committed yet.

## What an interviewer might ask

**Q: Why use experiment tracking instead of a spreadsheet?**
A: It records params, metrics, data fingerprint, code version and the model file automatically, at the
moment of training, so nothing is retyped or forgotten. And it's queryable: I found a reproducibility
bug by listing every run of the same model and seeing three different answers.

**Q: What makes a run reproducible?**
A: Same code (git commit, and flag uncommitted changes), same data (fingerprint), same seeds,
same package versions, and no hidden randomness. Ours had hidden randomness: a tie-break that
depended on multi-threaded row order. Fixing it made two runs give exactly 7,962 hits.

**Q: The runs differ by 30 buyers. Does that matter?**
A: It's 0.04 points, but the ranker's whole gain over the simple rule is 0.12 points. If noise is a
third of your effect, you can't trust a single run. That supports L45's caveat; I'd want several
weeks or seeds before claiming the ranker wins.

**Q: Why did MLflow refuse to save the ranker?**
A: MLflow 3 uses skops, a safer alternative to pickle, which only loads approved types. Rather than
approve LGBMRanker, I logged the native LightGBM booster (a text format that can't execute code). In
production, don't load pickles from places you don't fully trust.

**Q: Hyperparameter tuning barely moved AUC (0.7956-0.7965). What does that tell you?**
A: The information in the 13 clues limits the model, not its settings. Going from 5 to 13 clues gained
more (0.793 → 0.796) than any tuning. Next gains would come from new data (e.g. browsing,
returns), not more trees.
