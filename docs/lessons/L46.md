# Lesson 46: Product photos to CLIP embeddings (M9 Computer vision starts)

Scripts: `scripts/vision_download.py` (get the photos), `scripts/vision_embed.py` (turn them into numbers)
Module: M9 Computer vision (lesson 1 of 2)

## The idea in one paragraph

A computer can't "see" a dress, but it can compare lists of numbers. A pretrained vision
model turns each product photo into a list of 512 numbers, called an **embedding**. Photos
that look alike get similar lists. Once every photo is a list of numbers, "find items that
look like this one" becomes "find the closest lists", which is simple maths. This lesson
builds those embeddings and checks they make sense. Lesson 47 then uses them to recommend.

## Important: we used a subset

The plan was 3,000 photos. Kaggle's download limit (HTTP 429 = "Too Many Requests") kept
stopping us, so we stopped at **1,935 photos (469 MB)**. 5 articles have no photo on Kaggle at all.
Because the download went in sales order, the subset is roughly the **top ~1,940 sellers**.
These are the items customers are most likely to own, so that's the most useful part to have.

## The result first

| Check | CLIP neighbours | Random pair (chance) |
|---|---:|---:|
| Nearest photo has the same product type | **73.8%** | 6.9% |
| Nearest photo has the same colour group | **59.2%** | 17.5% |

The model was never told what a "Trousers" or a "Bra" is, yet its nearest neighbour has the
same product type 3 times out of 4. That's about 11x better than chance.

## Key words

- **Pretrained model**: a model someone else already trained on huge data (CLIP saw 400 million
  image-caption pairs from the internet). We just use it. We don't train it.
- **CLIP**: a model that learned to put a photo and its caption close together. That's why it
  can match photos to photos *and* photos to words.
- **ViT-B/32**: "Vision Transformer, Base size, 32x32-pixel patches", the small, CPU-friendly
  CLIP version.
- **Embedding**: the list of 512 numbers that summarises a photo.
- **Cosine similarity**: how much two embeddings point the same way. 1 = identical direction,
  0 = unrelated.
- **CPU vs GPU**: GPUs are much faster for these models. CPU works fine for 2,000 photos (about 3.5 minutes).

Download into the temp folder first, and **move it into place only when complete**. If the
script dies halfway through a file, the half-file is in `_tmp` (wiped next time), never in the

```python
        except Exception as e:
            msg = str(e)
            if "404" in msg or "Not Found" in msg:
                missing.add(a)
                missing_file.write_text("\n".join(sorted(missing)))
```

Two kinds of failure:
- **404 (no such file)**: record it as missing and move on instead of crashing.
- **429 (too many requests)**: wait, and double the wait each time: 15 s, 30 s, 60 s, 120 s...

## Part 2: embedding (`vision_embed.py`)

```python
import os
from pathlib import Path
os.environ.setdefault("HF_HUB_DISABLE_SYMLINKS_WARNING", "1")
import numpy as np
import open_clip
import polars as pl
import torch
from PIL import Image
```
`open_clip` provides CLIP models. `torch` (PyTorch) runs them. `PIL` (Pillow) opens JPG files.
The `os.environ` line only hides a harmless Windows warning about the model download cache.

```python
SEED = 46
np.random.seed(SEED)
torch.manual_seed(SEED)
torch.set_num_threads(8)
```
Seeds make the random example picks repeatable. The model itself has no randomness in
`eval` mode. `set_num_threads(8)` uses all 8 CPU threads on this laptop.

```python
pick = pl.read_parquet("data/clean/vision_articles.parquet")
assert pick.height == 3000
pick = pick.with_columns(
    pl.col("article_id").map_elements(lambda a: f"data/images/{a[:3]}/{a}.jpg", return_dtype=pl.String).alias("path")
)
pick = pick.filter(pl.col("path").map_elements(lambda p: Path(p).exists(), return_dtype=pl.Boolean))
```
Build each photo's file path and keep only articles whose photo exists. Output:
**1,935 of 3,000**. `map_elements` runs a small Python function on every row. It's slower than
normal polars, but fine for 3,000 rows.

```python
model, _, preprocess = open_clip.create_model_and_transforms("ViT-B-32-quickgelu", pretrained="openai")
tokenizer = open_clip.get_tokenizer("ViT-B-32-quickgelu")
model.eval()
```
- Downloads the CLIP weights once (cached in `~/.cache/huggingface`).
- `preprocess` = the exact resize/crop/colour-scaling CLIP expects (224x224 pixels).
- `tokenizer` turns words into numbers for the text half of CLIP.
- `model.eval()` = prediction mode (no training behaviour).

**Gotcha we hit:** with plain `"ViT-B-32"` the library warned *"QuickGELU mismatch"*. OpenAI trained
these weights with a slightly different internal activation function (QuickGELU). Using the
wrong one doesn't crash. It just gives slightly wrong numbers:

| Model name | Same product type as nearest photo |
|---|---:|
| `ViT-B-32` (mismatched, trial run) | 72.5% |
| `ViT-B-32-quickgelu` (correct) | **73.8%** |

Lesson: read warnings, because a quiet mismatch can cost accuracy without anything visibly breaking.

```python
paths, vecs = pick["path"].to_list(), []
with torch.no_grad():
    for i in range(0, len(paths), 64):
        batch = torch.stack([preprocess(Image.open(p).convert("RGB")) for p in paths[i:i + 64]])
        v = model.encode_image(batch)
        vecs.append((v / v.norm(dim=-1, keepdim=True)).numpy())
```
- `torch.no_grad()`: we're not training, so skip the bookkeeping. That's faster and uses less memory.
- Process **64 photos at a time** (a batch). That's faster than one by one, and lighter than all at once.
- `.convert("RGB")`: some JPGs are greyscale, and the model needs 3 colour channels.
- `torch.stack`: 64 images of shape 3x224x224 become one block of 64x3x224x224.
- `encode_image`: the actual CLIP step. 64 photos become 64 x 512 numbers.
- `v / v.norm(...)`: scale each list to length 1. Then the **dot product of two lists equals their
  cosine similarity**, which makes the next step a single matrix multiplication.

```python
emb = np.vstack(vecs).astype(np.float32)
assert emb.shape == (pick.height, 512)
```
Stack the batches into one table: 1,935 rows x 512 columns. The assert checks nothing was lost.

```python
sim = emb @ emb.T
np.fill_diagonal(sim, -1)
nn = np.argsort(-sim, axis=1)[:, :5]
```
- `emb @ emb.T`: similarity of every photo with every other photo, a 1,935 x 1,935 table
  (3.7 million numbers, calculated in well under a second).
- `fill_diagonal(sim, -1)`: an item is always most similar to itself, so hide that.
- `argsort(-sim)[:, :5]`: for each row, the positions of the 5 highest similarities.

Tiny before/after for one row (numbers from the output):

| Item | Raw similarities (excerpt) | Nearest 3 |
|---|---|---|
| Cindy cropped LS (Top) | itself 1.00 -> hidden; Apollo 0.98; Lion top 0.98; Haze LS 0.98; ... | Apollo Seamless Cropped LS, Lion top, Haze LS |

```python
arts = pl.read_parquet("data/parquet/articles.parquet").select(
    ["article_id", "prod_name", "product_type_name", "colour_group_name"])
meta = pick.select("article_id").join(arts, on="article_id", how="left")
assert meta.height == pick.height
```
Product names and categories, in the **same order** as the embedding rows. The assert makes
sure the join didn't add or drop rows, which would misalign everything.

```python
for col in ["product_type_name", "colour_group_name"]:
    v = meta[col].to_numpy()
    same_nn = (v[nn[:, 0]] == v).mean()
    share = meta[col].value_counts(normalize=True)["proportion"].to_numpy()
    chance = (share ** 2).sum()
```
- `v[nn[:, 0]]`: the category of each item's nearest neighbour. Comparing with `v` gives "same or
  not", and `.mean()` the share.
- **Chance baseline:** if 30% of items are trousers, two random items are both trousers
  0.3 x 0.3 = 9% of the time. Summing that over all categories gives the chance of a random match.
  Without this, "73.8%" has nothing to compare against.

| | Same product type | Same colour group |
|---|---:|---:|
| Random pair | 6.9% | 17.5% |
| CLIP nearest neighbour | 73.8% | 59.2% |

Colour is weaker, because CLIP judges shape and style first, and lighting varies between photos.

## What an interviewer might ask

**Q: Why use a pretrained model instead of training your own?**
A: Training a vision model needs millions of labelled images and GPUs. CLIP already learned general
visual concepts from 400M image-text pairs. For "find similar items" we just reuse its embeddings:
this is called **transfer learning** / using a **foundation model**.

**Q: How did you check the embeddings are any good without labels?**
A: Used the product catalogue as a free label. The nearest neighbour shares the product type 73.8% of the
time vs 6.9% for random pairs. Then I looked at examples by eye. Always compare against a chance
baseline.

**Q: Why normalise the vectors?**
A: After scaling to length 1, the dot product equals cosine similarity, so all-pairs similarity
is a single matrix multiply (`emb @ emb.T`). It also stops "bigger" vectors from dominating.

**Q: This won't scale to 100k items. What would you do?**
A: The all-pairs matrix grows with items squared (100k^2 = 10 billion numbers). Use an
**approximate nearest neighbour** index (FAISS, Annoy, or a vector database), which finds near
neighbours without comparing everything. A GPU would also make embedding 100k photos fast.

**Q: Your download was interrupted. How did you avoid corrupted files?**
A: Download to a temp folder and only move the file into place once complete. Skip files that
already exist, so reruns resume. Handle 429 with exponential back-off and 404 by recording the
article as missing.

**Q: What's a weakness of CLIP similarity for fashion?**
A: It focuses on overall look and category. Similarity scores are compressed (0.96-0.98) because
studio photos look alike, and it can miss things shoppers care about (fit, fabric, price). It
also says nothing about whether someone *wants* a second near-identical item. Lesson 47 tests
exactly that.
