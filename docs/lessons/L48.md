## The idea in one paragraph

Every H&M article has a short description (`detail_desc`), like *"Wide, sleeveless top in soft
jersey with a metallic print."* In Lesson 46 we turned **photos** into numbers. Here we turn
**text** into numbers in two ways, an old-school word-count method (TF-IDF) and a modern neural
model (MiniLM). Then we run the same sanity check: does "most similar description" really
mean "same kind of product"?

## The result first

10,000 products, one colour each:

| Nearest description has the same... | Product type | Colour | Department |
|---|---:|---:|---:|
| Random pair (chance) | 4.5% | 11.8% | 1.1% |
| TF-IDF (word counts) | 72.2% | 24.8% | 36.3% |
| **MiniLM (sentence model)** | **80.1%** | 24.5% | **37.4%** |

The 1,935 items that have photos (from L46):

| Nearest neighbour has the same... | Product type | Colour | Department |
|---|---:|---:|---:|
| Photo (CLIP image) | 70.5% | **61.0%** | 42.1% |
| Text (MiniLM) | 78.4% | 31.4% | 50.6% |
| **Photo + text** | **81.6%** | 46.9% | **53.9%** |

**Text knows *what* an item is. The photo knows *what colour* it is.** Together they are best at
type and department.

## Key words

- **TF-IDF** (Term Frequency x Inverse Document Frequency): count the words in each text, but
  give rare words more weight ("sequin" says more than "with"). Two texts are similar if they
  share important words.
- **Sentence embedding**: a neural model reads the whole sentence and outputs a fixed list of
  numbers (384 for MiniLM). Texts with similar *meaning* get similar lists, even with different words.
- **MiniLM** (`all-MiniLM-L6-v2`): a small, free sentence model (about 90 MB) that runs fine on a laptop CPU.
- **Stop words**: very common words ("the", "with", "and") that TF-IDF ignores.
- **Bigram**: a two-word phrase, like "short sleeves".

## A trap we avoided: colour variants share the same text

Before writing any code we profiled the descriptions:

| Fact | Number |
|---|---:|
| Articles | 105,542 |
| Missing description | 416 |
| Products sold in more than one colour | 23,061 |
| ...of those, with the *identical* description in every colour | **100%** |

The black and the white version of a top have the same text. If we compared all articles, nearly
every item's "most similar description" would be *itself in another colour*: 100% similarity,
trivially the same type. The test would look perfect and mean nothing. So we keep **one article per
product** for the benchmark. For the photo comparison we keep all articles but forbid other colours of
the same product as neighbours.

```python
def nearest(emb, codes=None, block=1000):
    n, out = emb.shape[0], np.empty(emb.shape[0], dtype=np.int64)
    for s in range(0, n, block):
        sim = emb[s:s + block] @ emb.T
        sim = sim.toarray() if hasattr(sim, "toarray") else np.asarray(sim)
        sim[np.arange(sim.shape[0]), np.arange(s, s + sim.shape[0])] = -np.inf
        if codes is not None:
            sim[codes[s:s + block, None] == codes[None, :]] = -np.inf
        out[s:s + block] = sim.argmax(axis=1)
    return out
```
This finds each item's most similar other item **1,000 rows at a time**.

Why not do it all at once like L46? A full 10,000 x 10,000 similarity table is 100 million numbers
(400-800 MB each). Our first version kept several of them in memory (plus copies) while other
programs were running, and the laptop got down to 1 GB of free memory. In blocks, only a
1,000 x 10,000 slice exists at any moment (40 MB).

| Approach | Biggest table in memory |
|---|---:|
| Full matrix (first version) | 10,000 x 10,000 = 100M numbers, several at once |
| Blocks of 1,000 (now) | 1,000 x 10,000 = 10M numbers |

- `emb[s:s+block] @ emb.T`: similarity of 1,000 items with all items.
- `.toarray()`: TF-IDF data is **sparse** (mostly zeros, stored compactly). We turn just this
  slice into a normal table.
- The `-np.inf` line: an item may not pick itself. `-inf` = "infinitely dissimilar".
- `codes`: optionally, it also may not pick another colour of the same product.
- `argmax(axis=1)`: the position of the highest similarity in each row.

```python
def embed_minilm(t):
    m = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2", device="cpu")
    return m.encode(t, batch_size=128, normalize_embeddings=True, show_progress_bar=False).astype(np.float32)
```
Downloads MiniLM once (about 90 MB), then turns each text into 384 numbers. `normalize_embeddings=True`
scales each list to length 1, so a dot product equals cosine similarity (the same trick as L46).

```python
cols = ["product_type_name", "colour_group_name", "department_name"]

def score(nn, meta):
    return {c: (meta[c].to_numpy()[nn] == meta[c].to_numpy()).mean() for c in cols}

chance = {c: (bench[c].value_counts(normalize=True)["proportion"].to_numpy() ** 2).sum() for c in cols}
```
`score`: the share of items whose neighbour has the same type / colour / department.
`chance`: how often two *random* items match (the sum of squared shares, as in L46). We need it to
judge whether 80% is impressive. With 131 product types, random pairs match only 4.5% of the time.

```python
tfidf = TfidfVectorizer(ngram_range=(1, 2), min_df=2, sublinear_tf=True, stop_words="english")
X = tfidf.fit_transform(texts).astype(np.float32)
```
- `ngram_range=(1, 2)`: use single words *and* two-word phrases ("short sleeves").
- `min_df=2`: ignore words that appear in only one description (typos, rare names).
- `sublinear_tf=True`: a word used 3 times counts less than 3x as much.
- `stop_words="english"`: drop "the", "with", "and"...
- TF-IDF rows already have length 1, so the same `nearest` function works.

Output: **11,823** words and word-pairs in the vocabulary.

Tiny illustration of the two methods (made-up texts):

| Text A | Text B | TF-IDF | MiniLM |

| "vest top in jersey" | "sleeveless top in jersey" | partly similar (shares "top", "jersey") | very similar (vest = sleeveless) |
| "vest top in jersey" | "jersey dress" | partly similar (shares "jersey") | less similar (a dress is a different thing) |

Each method's neighbours. TF-IDF takes about 4 seconds; MiniLM about 2 minutes (a neural network

### Text vs photo

```python
img = pl.read_parquet("data/clean/image_embeddings.parquet")
photo = img.select("article_id").join(arts, on="article_id", how="left")
assert photo.height == img.height and photo["detail_desc"].null_count() == 0

```
Load the 1,935 photo embeddings from L46 and attach each article's description, in the same row
order. The assert checks every photo item has a description. `codes` lets us forbid
same-product neighbours.

```python
both = np.hstack([im, tx_emb]) / np.sqrt(2)
```
**Combining two embeddings:** glue the photo list (512 numbers) and the text list (384 numbers)
side by side, giving 896 numbers. Each part has length 1, so the glued list has length sqrt(2), and
dividing by sqrt(2) brings it back to 1. The similarity of two glued lists is then exactly the
*average* of photo similarity and text similarity.

```python
for name, e in [("Image (CLIP photo)", im), ("Text (MiniLM)", tx_emb), ("Image + text", both)]:
    r = score(nearest(e, codes), photo)
```
That gives the second results table:
- Text beats photo on **type** (78.4% vs 70.5%): the words literally say "trousers".
- Photo crushes text on **colour** (61.0% vs 31.4%): the text never says the colour.
- Combined is best on **type** (81.6%) and **department** (53.9%), and in between on colour.

**A correction to Lesson 46.** There, the photo check said 73.8% same type. With other colours of the same
product excluded, it's **70.5%**. Some of L46's matches were the same garment in another colour.
The conclusion (far above chance) still holds, but this check is the fairer one.

## Why we dropped CLIP's text encoder

The plan was to also test CLIP's *text* half, which puts words in the same space as photos.
One full run did finish and scored **80.5%** same type (MiniLM 80.1%), a tie. But it took
**about 15 minutes** for the 10,000 descriptions, vs about 2 minutes for MiniLM.

We spent a 10-minute investigation on whether it was a bug:

| Test (500 descriptions) | Time |
|---|---:|
| CLIP text alone, 8 threads | 40.3 s |
| CLIP text after MiniLM in the same program, 8 threads | 43.8 s |
| CLIP text alone, 4 threads | 71.8 s |
| CLIP text alone, 8 threads, smaller batches of 32 | 32.4 s |

It's equally slow on its own, so it isn't two models fighting over threads. It's simply heavier.
It pads every description to 77 tokens (MiniLM uses only the length it needs), and its text
network is about 3x bigger. Same quality at 7x the time means it isn't worth it here.

## What an interviewer might ask

**Q: TF-IDF or embeddings, which would you use?**
A: Start with TF-IDF. It's instant, explainable ("they share the words 'metallic' and 'jersey'") and
a strong baseline (72%). Use a sentence model when meaning matters more than exact words: it got
80% here by matching "vest top" with "T-shirt". Always measure both on your own data.

**Q: Your first sanity check would have scored almost 100%. Why?**
A: Colour variants share identical descriptions, so the nearest neighbour would be the same
product. I deduplicated to one article per product, and for the photo comparison excluded
same-product neighbours. Always ask what could make a metric trivially high.

**Q: How do you combine text and image embeddings?**
A: Normalise each, concatenate, and renormalise. The cosine similarity then equals the average of the
two similarities. You could weight them (e.g. 70% text) or learn the weights. Here a plain
average gave the best type match (81.6%).

**Q: How did you handle memory?**
A: Block-wise nearest neighbours: 1,000 rows at a time, so only a small slice of the similarity
matrix exists at any moment. At larger scale you'd use an approximate nearest-neighbour index
(FAISS, a vector database).

**Q: Why did you drop the CLIP text model?**
A: It tied MiniLM on quality (80.5% vs 80.1%) but was about 7x slower on CPU. I profiled it first, to
rule out a fixable threading problem, before deciding. Speed is a legitimate model-selection criterion.

**Q: Why is colour accuracy low for text?**
A: The description is shared across colours, so it contains no colour words. Text can only infer
colour from type (basics are often black). That's why the photo and the text complement each other.
